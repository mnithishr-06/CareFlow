# CareFlow Data Dictionary and Metric Catalog

## 1. Scope and interpretation

This document defines the event-log schema, canonical pathway, and the fields and calculations in the processed outputs under `data/processed/`. The checked-in data is a **synthetic demonstration dataset** generated by `src/generate_synthetic.py`: 500 cases, 500 patients, and 3,500 events. Timestamps, departments, provider IDs, and severity values are generated; they are not real clinical observations.

The definitions below describe the current implementation. They are not approved clinical definitions or operational SLAs. In particular, the seven-stage path is a configured reference sequence, the current generator creates only that full sequence, and the SLA thresholds are examples. These outputs must not be used to guide patient care, assert real-world SOP adherence, or make staffing/capacity decisions.

## 2. Source event log: `data/raw/clinical_events.csv`

One row represents one activity/event for a patient case. The generator writes the columns below in this order. CSV values are text on disk; “logical type” describes the intended parsed value.

| Column | Logical type | Definition | Constraints in generated data / loader | Example |
|---|---|---|---|---|
| `case_id` | String identifier | Identifier for one pathway instance (case). | Required by loader; non-empty in generated data; each case is associated with one patient. The loader does not explicitly reject blank or repeated case IDs. | `C00001` |
| `patient_id` | String identifier | Synthetic patient identifier. | Required by loader; generated consistently across all events in the case. The loader does not enforce one case per patient. | `P00001` |
| `severity` | Categorical string | Synthetic cohort label assigned once per generated patient. | Values generated from `High`, `Moderate`, `Low`; not clinically assessed and not required by the base loader. | `High` |
| `event_name` | Categorical string | Name of the activity performed in this event. | Canonical generated values are the seven milestones in §3. Loader accepts `activity` as an alias when `event_name` is absent. Loader checks each case has seven distinct event names; downstream pathway analyses further require exactly one of each expected milestone. | `Emergency_Admission` |
| `event_timestamp` | ISO-like datetime string; parsed to datetime | Time associated with the event. | Generated in ISO format with a space separator and no timezone marker. Loader parses values with `pandas.to_datetime`; it does not enforce timezone awareness or reject every null identifier. Alias `timestamp` is accepted if `event_timestamp` is absent. | `2026-02-09 19:44:40` |
| `department` | String / categorical label | Department recorded for this event. | Required by loader; generated from `ED`, `Triage`, `Lab`, `Consult`, `OR`, `Ward`. Assignment is synthetic and per event; department ownership of a transition is inferred from its destination event in SLA reporting. | `Consult` |
| `provider_id` | String identifier | Synthetic provider identifier for the event. | Generated as `DR` followed by three digits; not required by loader. No provider-level analytics in the current metric catalog. | `DR501` |

### Input validation and supported aliases

`src/data_loader.py` requires `case_id`, `patient_id`, and `department`, plus an event-name column (`event_name` or `activity`) and timestamp column (`event_timestamp` or `timestamp`). It normalizes aliases to `event_name` and `event_timestamp`, parses timestamps, checks each case has seven distinct event names, and sorts by case and timestamp.

That loader check is not a full integrity guarantee: it counts distinct event names, not expected-name membership or the per-name occurrence count. Analyses such as transition metrics, SLA, cohort, process map, and simulation perform stricter checks requiring each expected milestone exactly once and a nondecreasing canonical timestamp sequence. `src/variant_analysis.py` is intentionally more permissive so it can discover variants. `src/anomaly_detection.py` has its own permissive loader so it can report incomplete traces rather than rejecting them.

## 3. Canonical clinical milestones

The standard path is the ordered tuple below. For a standard complete case, each milestone occurs exactly once and timestamps are nondecreasing in this order.

| Order | Event value | Display name |
|---:|---|---|
| 1 | `Emergency_Admission` | Emergency Admission |
| 2 | `Triage_Assessment` | Triage Assessment |
| 3 | `Diagnostic_Lab_Orders` | Diagnostic Lab Orders |
| 4 | `Physician_Consultation` | Physician Consultation |
| 5 | `Treatment_or_Surgery` | Treatment or Surgery |
| 6 | `Inpatient_Ward_Transfer` | Inpatient Ward Transfer |
| 7 | `Discharge` | Discharge |

Notation used below:

- $c$ denotes a case/patient pathway, and $C$ is the set of cases included by a metric.
- $t_{c,k}$ is the timestamp (datetime) for case $c$'s milestone $k$, with $k=1,\ldots,7$.
- Durations are elapsed wall-clock seconds divided by 3,600, expressed in hours. The pipeline does not apply business-hours calendars, timezone conversion, pause rules, or exclusions.
- For SLA-targeted transition $q$, $W_{c,q}$ is the elapsed hours and $T_q$ is its configured target.

## 4. Processed data catalog

All CSV files are UTF-8/CSV outputs written by the analytics scripts. Numeric CSV fields should be parsed as numeric types; boolean fields are serialized as `True`/`False` by pandas or Python CSV writers. Empty anomaly output and empty breach output are header-only CSVs. The current checked-in outputs reflect the current synthetic data and may be regenerated.

### 4.1 `transition_metrics.csv`

**Purpose:** Descriptive case LoS and transition-wait distribution summaries; includes a duplicate summary row marking the longest-mean transition.

| Column | Type | Definition |
|---|---|---|
| `metric` | String category | `patient_los`, `transition_wait`, or `top_bottleneck`. |
| `stage` | String | `Length_of_Stay` for LoS; destination milestone for a transition. |
| `from_stage` | String | Start milestone for the interval. |
| `to_stage` | String | End milestone for the interval. |
| `patient_count` | Integer | Number of cases in the duration sample. |
| `mean_duration_hours` | Float | Arithmetic mean of case durations, in hours. |
| `median_duration_hours` | Float | Median of case durations, in hours. |
| `min_duration_hours` | Float | Minimum observed duration, in hours. |
| `max_duration_hours` | Float | Maximum observed duration, in hours. |

For each complete case:

$$
L_c = \frac{t_{c,7}-t_{c,1}}{3600\ \mathrm{seconds/hour}}
\qquad
W_{c,k} = \frac{t_{c,k}-t_{c,k-1}}{3600\ \mathrm{seconds/hour}},
\quad k=2,\ldots,7
$$

For any metric's duration sample $X=\{x_1,\ldots,x_n\}$:

- `patient_count` $=n$
- `mean_duration_hours` $=\frac{1}{n}\sum_{i=1}^{n}x_i$
- `median_duration_hours` $=\operatorname{median}(X)$ (for an even sample, pandas/statistics median averages the two central values)
- `min_duration_hours` $=\min(X)$; `max_duration_hours` $=\max(X)$
- `patient_los` summarizes $\{L_c\}$.
- Each `transition_wait` row summarizes $\{W_{c,k}\}$ for one consecutive milestone pair.
- `top_bottleneck` repeats the transition row whose mean $W$ is maximum; ties follow the first encountered milestone order in the implementation.

**Current synthetic result:** median LoS 27.125 h; maximum mean transition is Inpatient Ward Transfer → Discharge at 13.651233 h.

### 4.2 `process_graph_edges.csv`

**Purpose:** Edge list for the canonical consecutive-stage process map.

| Column | Type | Definition |
|---|---|---|
| `source` | String | Source milestone. |
| `target` | String | Next milestone in the edge. |
| `patient_count` | Integer | Cases contributing a valid wait observation to this edge. |
| `mean_waiting_hours` | Float | Arithmetic mean elapsed time for the edge, in hours. |

For edge $e=(s,t)$, let $C_e$ be cases with exactly one event at both stages and valid canonical timestamp order. Then:

$$
\text{patient\_count}_e=|C_e|,\qquad
\text{mean\_waiting\_hours}_e=
\frac{1}{|C_e|}\sum_{c\in C_e}\frac{t_{c,t}-t_{c,s}}{3600}
$$

The current data has six edges and 500 cases per edge. The process map visualization highlights the edge with maximum mean wait; it does not infer a cause.

### 4.3 `pathway_variants.csv`

**Purpose:** Frequency distribution of distinct timestamp-ordered event-name sequences.

| Column | Type | Definition |
|---|---|---|
| `variant_id` | String | Rank-based identifier `V001`, `V002`, etc. |
| `pathway` | String | Event names joined in observed chronological order using ` -> `. |
| `patient_count` | Integer | Number of cases with exactly this ordered sequence. |
| `patient_percentage` | Float | Percent of all cases represented by this sequence. |
| `is_standard_happy_path` | Boolean | True only if the tuple equals all seven canonical milestones in order. |
| `standard_happy_path_adherence_percentage` | Float | Overall share of cases exactly matching the canonical tuple; repeated on every row. |

For variant $v$, $n_v$ is its case count and $N$ is total cases:

$$
\text{patient\_percentage}_v=100\frac{n_v}{N},\qquad
\text{adherence}=100\frac{\sum_{c\in C}\mathbf{1}[\mathrm{path}(c)=\mathrm{canonical}]}{N}
$$

Variants are ordered by descending count, then lexicographic tuple order. The sequence is sorted by case and timestamp before grouping. This calculation does not independently validate exactly-one occurrence per milestone; it records observed sequences, including repeats or deviations.

### 4.4 `rework_summary.csv`

**Purpose:** Activity-level counts for activities repeated within a case.

| Column | Type | Definition |
|---|---|---|
| `activity` | String | Repeated event name; `None detected` is a sentinel row when no repeats exist. |
| `patient_count` | Integer | Distinct cases in which that activity occurs more than once. |
| `extra_occurrences` | Integer | Total occurrences beyond the first, summed over affected cases. |
| `total_occurrences` | Integer | All occurrences of the activity across affected cases (cases with at least two occurrences only). |
| `patient_percentage` | Float | Affected cases divided by all cases, times 100. |

For activity $a$, let $n_{c,a}$ be its event count in case $c$, and define affected cases $R_a=\{c:n_{c,a}>1\}$:

$$
\text{patient\_count}_a=|R_a|,\quad
\text{extra\_occurrences}_a=\sum_{c\in R_a}(n_{c,a}-1),\quad
\text{total\_occurrences}_a=\sum_{c\in R_a}n_{c,a},\quad
\text{patient\_percentage}_a=100\frac{|R_a|}{N}
$$

When there are no repeated activities the output has one `None detected` row with all counts and percentage zero; that row is not a clinical activity.

### 4.5 `sla_violations.csv`

**Purpose:** Detailed breach-only audit records for configured SLA transitions. A compliant transition is not emitted.

Configured targets in `src/sla_compliance.py`:

| Source | Target | Target $T_q$ |
|---|---|---:|
| Triage Assessment | Physician Consultation | 1.0 h |
| Inpatient Ward Transfer | Discharge | 4.0 h |

| Column | Type | Definition |
|---|---|---|
| `case_id` | String identifier | Case with the breach. |
| `patient_id` | String identifier | Patient ID from the destination event. |
| `source` | String | SLA transition's source milestone. |
| `target` | String | SLA transition's destination milestone. |
| `department` | String | Department recorded on the destination event; this is the reporting attribution convention. |
| `actual_waiting_hours` | Float | $W_{c,q}=(t_{\mathrm{target}}-t_{\mathrm{source}})/3600$. |
| `sla_target_hours` | Float | Configured $T_q$, in hours. |
| `breach_hours` | Float | Excess over target: $W_{c,q}-T_q$. |

A record is emitted only when $W_{c,q}>T_q$ (strict greater-than; equality is compliant). Thus:

$$
\text{breach}_{c,q}=\mathbf{1}[W_{c,q}>T_q],\quad
\text{breach\_hours}_{c,q}=W_{c,q}-T_q\quad\text{for breach rows only}
$$

An empty file means no violations were recorded, not that no transitions were evaluated. This breach-only file alone cannot provide compliance rate or the number of compliant transitions. The companion department summary contains denominators.

### 4.6 `department_breach_summary.csv`

**Purpose:** Aggregate evaluation and breach metrics by destination-event department across both configured SLA transitions.

| Column | Type | Definition |
|---|---|---|
| `department` | String | Destination department receiving attribution. |
| `transitions_evaluated` | Integer | Number of targeted transition observations assigned to the department, compliant or not. |
| `breaches` | Integer | Observations exceeding their target. |
| `compliant_transitions` | Integer | Evaluated observations minus breaches. |
| `compliance_percentage` | Float | Compliant observations divided by evaluated observations, times 100. |
| `mean_waiting_hours` | Float | Mean duration across all evaluated targeted transitions in that department. |
| `max_waiting_hours` | Float | Maximum duration among those evaluated transitions. |
| `total_breach_hours` | Float | Sum of excess hours for breach observations. |

For department $d$, let $E_d$ be its evaluated transitions and $B_d\subseteq E_d$ its breaches:

$$
\begin{aligned}
\text{transitions\_evaluated}_d &= |E_d|\\
\text{breaches}_d &= |B_d|\\
\text{compliant\_transitions}_d &= |E_d|-|B_d|\\
\text{compliance\_percentage}_d &=100\frac{|E_d|-|B_d|}{|E_d|}\\
\text{mean\_waiting\_hours}_d &=\frac{1}{|E_d|}\sum_{e\in E_d}W_e\\
\text{max\_waiting\_hours}_d &=\max_{e\in E_d}W_e\\
\text{total\_breach\_hours}_d &=\sum_{e\in B_d}(W_e-T_e)
\end{aligned}
$$

Each case contributes two evaluations, but departments are determined separately for each destination event. Therefore a case can contribute to two different departments.

### 4.7 `cohort_metrics.csv`

**Purpose:** Compare patient-level descriptive measures across a cohort column, defaulting to synthetic `severity`.

| Column | Type | Definition |
|---|---|---|
| `cohort` | String | One patient-level cohort value; all events within a case must agree. |
| `patient_count` | Integer | Distinct cases in the cohort. |
| `median_los_hours` | Float | Median admission-to-discharge duration across cases. |
| `mean_transition_wait_hours` | Float | Mean of patient-level mean waits, where each patient's mean uses all six consecutive transitions. |
| `sla_transitions_evaluated` | Integer | Two targeted SLA transitions per case summed in the cohort. |
| `sla_breaches` | Integer | Count of target transitions above their configured thresholds. |
| `sla_compliant_transitions` | Integer | Evaluated transitions minus breaches. |
| `sla_breach_rate_percentage` | Float | Breaches divided by evaluated transitions, times 100. |

For cohort $g$, $C_g$ is its case set; $L_c$ is case LoS, $W_{c,k}$ is one of its six consecutive-stage waits, $Q=2$ is the number of configured SLA checks per case, and $B_c$ is that case's breach count:

$$
\begin{aligned}
\text{patient\_count}_g &= |C_g|\\
\text{median\_los\_hours}_g &= \operatorname{median}_{c\in C_g}(L_c)\\
\text{mean\_transition\_wait\_hours}_g
&=\frac{1}{|C_g|}\sum_{c\in C_g}\left(\frac{1}{6}\sum_{k=2}^{7}W_{c,k}\right)\\
\text{sla\_transitions\_evaluated}_g &= Q|C_g|\\
\text{sla\_breaches}_g &= \sum_{c\in C_g}B_c\\
\text{sla\_compliant\_transitions}_g &= Q|C_g|-\sum_{c\in C_g}B_c\\
\text{sla\_breach\_rate\_percentage}_g
&=100\frac{\sum_{c\in C_g}B_c}{Q|C_g|}
\end{aligned}
$$

The generated `severity` categories are deterministic synthetic labels, not observed acuity. Comparisons are descriptive and do not establish causal relationships.

### 4.8 `conformance_scores.csv`

**Purpose:** One PM4Py token-based replay diagnostic row per case against the configured canonical seven-stage Petri net.

| Column | Type | Definition |
|---|---|---|
| `case_id` | String identifier | Replayed case. |
| `trace_is_fit` | Boolean | PM4Py replay's fit flag for the trace. |
| `trace_fitness` | Float | PM4Py token-based replay fitness score, generally in $[0,1]$, with 1 indicating a fit trace. |
| `missing_tokens` | Integer | Tokens required but missing during replay. |
| `remaining_tokens` | Integer | Tokens left in the final marking after replay. |
| `consumed_tokens` | Integer | Tokens consumed by replay. |
| `produced_tokens` | Integer | Tokens produced by replay. |

For the standard token-based replay fitness convention used by PM4Py:

$$
\mathrm{fitness}_c =
\frac{1}{2}\left[
\left(1-\frac{\mathrm{missing}_c}{\mathrm{consumed}_c}\right)
+\left(1-\frac{\mathrm{remaining}_c}{\mathrm{produced}_c}\right)
\right]
$$

The implementation stores PM4Py's returned fitness and token counts rather than recalculating the score. Zero-denominator/degenerate replay handling is PM4Py-defined. `trace_is_fit` is the package's replay diagnostic flag; do not infer it solely by thresholding the rounded score. Fitness is relative to this configured canonical model, not an independently approved SOP.

### 4.9 `conformance_summary.txt`

**Purpose:** Executive aggregate of `conformance_scores.csv`. It reports patient case count, fitting/non-fitting case counts, fit percentage, mean and median trace fitness, and sums of missing and remaining tokens.

For $N$ score rows and fit flag $F_c$:

$$
\begin{aligned}
\text{patient cases} &= N\\
\text{fitting cases} &= \sum_c \mathbf{1}[F_c]\\
\text{non-fitting cases} &= N-\text{fitting cases}\\
\text{trace fit percentage} &=100\frac{\text{fitting cases}}{N}\\
\text{mean fitness} &=\frac{1}{N}\sum_c\mathrm{fitness}_c\\
\text{median fitness} &=\operatorname{median}_c(\mathrm{fitness}_c)\\
\text{total missing tokens} &=\sum_c\mathrm{missing}_c,\quad
\text{total remaining tokens}=\sum_c\mathrm{remaining}_c
\end{aligned}
$$

The text report explicitly caveats that the event log is synthetic and the reference is only the configured canonical sequence.

### 4.10 `simulation_results.csv`

**Purpose:** Per-scenario, proportional what-if reduction of each case's Inpatient Ward Transfer → Discharge interval. It is not a queueing, census, staffing, demand, occupancy, or throughput model.

| Column | Type | Definition |
|---|---|---|
| `scenario` | String | `Baseline`, `30% reduction`, `50% reduction`, or `70% reduction`. |
| `discharge_delay_reduction_percentage` | Integer | Scenario reduction $p$, percent. |
| `patient_count` | Integer | Distinct cases simulated. |
| `baseline_mean_los_hours` | Float | Mean baseline LoS. |
| `simulated_mean_los_hours` | Float | Mean per-case LoS after reducing the discharge wait. |
| `mean_los_improvement_hours` | Float | Baseline mean LoS minus simulated mean LoS. |
| `baseline_median_los_hours` | Float | Median baseline LoS. |
| `simulated_median_los_hours` | Float | Median of individually simulated LoS values. |
| `median_los_improvement_hours` | Float | Baseline median minus simulated median. |
| `baseline_mean_discharge_delay_hours` | Float | Mean baseline transfer-to-discharge wait. |
| `simulated_mean_discharge_delay_hours` | Float | Mean transfer-to-discharge wait after reduction. |
| `total_bed_hours_saved` | Float | Sum of removed discharge-delay hours across cases. |

For case $c$, let baseline LoS $L_c$, discharge wait $D_c=t_{c,7}-t_{c,6}$, and reduction fraction $r=p/100$:

$$
\begin{aligned}
\mathrm{saved}_{c,p} &= rD_c\\
\mathrm{simulated\_LoS}_{c,p} &= L_c-rD_c\\
\mathrm{simulated\_discharge\_wait}_{c,p} &= (1-r)D_c\\
\mathrm{mean\_LoS}_{p} &= \frac{1}{N}\sum_c\mathrm{simulated\_LoS}_{c,p}\\
\mathrm{mean\_LoS\_improvement}_{p} &= \overline{L}-\mathrm{mean\_LoS}_{p}\\
\mathrm{median\_LoS}_{p} &= \operatorname{median}_c(\mathrm{simulated\_LoS}_{c,p})\\
\mathrm{median\_LoS\_improvement}_{p} &= \operatorname{median}(L)-\mathrm{median\_LoS}_{p}\\
\mathrm{total\_bed\_hours\_saved}_{p} &= \sum_c\mathrm{saved}_{c,p}
\end{aligned}
$$

Baseline is $p=0$. For the current 50% scenario, the generated data yields 6.8256 mean LoS hours improved per case and 3,412.8083 aggregate bed-hours saved (displayed as 6.83 and 3,412.81).

### 4.11 `clinical_anomalies.csv`

**Purpose:** Audit findings emitted by `src/anomaly_detection.py`. There is one record per detected anomaly, not one row per event or every valid case.

| Column | Type | Definition |
|---|---|---|
| `case_id` | String identifier | Case associated with the finding. |
| `patient_id` | String identifier / empty | First non-null patient ID in that case, when present. |
| `anomaly_type` | String category | `timestamp_inversion`, `extreme_wait_outlier`, or `incomplete_trace`. |
| `source_stage` | String / empty | Earlier stage in the checked canonical transition; empty for incomplete trace. |
| `target_stage` | String / empty | Later stage in the checked canonical transition; empty for incomplete trace. |
| `observed_wait_hours` | Float / empty | Signed elapsed wait for inversion, nonnegative wait for outlier; empty for incomplete trace. |
| `threshold_hours` | Float / empty | Mean plus three population standard deviations for the corresponding transition; empty unless outlier. |
| `details` | String | Human-readable note; incomplete traces list missing milestones. |

Detection rules:

- A case is marked `incomplete_trace` if one or more canonical milestones occur zero times. Multiple missing stages are listed in one record. Duplicate activity counts are not, by themselves, labeled incomplete by this rule.
- A `timestamp_inversion` is recorded for an adjacent canonical pair when each stage occurs exactly once and $W_{c,k}<0$.
- For each adjacent transition $k$, valid nonnegative waits $V_k$ are used to calculate population mean $\mu_k$ and population standard deviation $\sigma_k$ (`ddof=0`). A wait is an `extreme_wait_outlier` only if $W_{c,k}>\mu_k+3\sigma_k$. Inversions and cases lacking a unique event at either endpoint are excluded from that transition's outlier sample.

An empty/header-only file means the current run flagged no records under these rules; it is not evidence that a production stream is anomaly-free.

## 5. Reproduction

From the repository root, install `requirements.txt` and run the complete pipeline:

```shell
python main.py
```

For a headless run that skips the process-net and simulation chart rendering:

```shell
python main.py --skip-viz
```

The pipeline regenerates transition metrics, variants/rework, SLA outputs, the discovered PNML model, conformance outputs, simulation results, and `reports/clinical_executive_brief.md`. Other standalone scripts (such as cohort analysis, process-map generation, and anomaly detection) can be run individually to regenerate their outputs.
